# PITCH X/Growth Automation — Architecture & Rewrite Spec

**One document capturing the entire essence of the existing build so it can be
thrown away and rewritten from scratch with the right architecture.**

This repo was an autonomous X/Twitter growth + "demo robot" system for
**PITCH** (https://trypitch.co), an AI video editor that turns a task description
into a studio-quality narrated demo MP4 ("describe a demo, get a cinematic
narrated product video, no production team, no editing").

---

## 1. What the system did (the business logic that survives)

There are **two product surfaces**, both driven from X/Twitter and both
producing an AI-generated demo video via the **Pitch MCP** service
(`https://api.trypitch.co/mcp`):

### 1.1 The Mention Bot ("demo robot")
Anyone can tag `@trypitchdotco` with a product URL in a tweet ("hey @trypitchdotco make me a demo of https://foo.co"). The bot:

1. **Detects** the mention (via X webhook / browser polling).
2. **Acknowledges** with a quick reply ("we're on it, generating your cinematic demo for <url> now").
3. **Triggers** `create_demo_video` on Pitch MCP.
4. **Polls** Pitch MCP `get_job` until `COMPLETED`.
5. **Replies** back to the tweet thread with the S3 video URL ("Here is your product demo ... generated by @trypitchdotco!").
6. Tracks every job through a status machine in Supabase: `pending → rendering → delivered | failed | no_url_found | submitted`.

### 1.2 The Growth / CRM engine
Discover ICP (SaaS founders, growth people, agencies, creators, indie hackers) and run a warm-up → pitch → convert funnel:

- **Discovery:** search X for intent/competitor queries (`tella.tv`, `screen.studio`, `loom.com alternative`, `need a product demo video`, `how to make a product demo video`, launch signals, `_filter:replies` founder queries).
- **Scoring:** each prospect gets a 1–10 score (has URL +2, mentions competitors +2, shows intent +1).
- **CRM stages:** `new → warming → contacted → in_convo → trial → customer → do-not-contact | lost`.
- **Warm-up:** like 1–2 posts + one genuinely useful reply (never pitch in a first reply).
- **Outreach:** DM only after warming, lead with value (offer a free demo of *their* product), personalize every message, honor opt-outs forever.
- **Learning loop:** DM openers tagged with a `variant`; reply/conversion outcomes feed `stats.sh`; `insights.md` biases toward winning variants with a ~10-20% exploration slot.
- **Product Hunt trigger:** when someone launches on Product Hunt and tweets about it, auto-send congrats + auto-generate a launch demo video.

### 1.3 Content / community / trend scoring
- Original posts, quote-tweets, memes, replies on tech-founder topics (AI tooling, devtools, SaaS, launch pages).
- Trend-jacking around Polymarket, startup/AI news, tech Twitter narratives.
- Public "help-first" community presence for @trypitchdotco.

## 3. Integration contract (what the rewrite must connect to)

### 3.1 X / Twitter (three access modes)
- **X API v2 (primary):** OAuth2 user context.
  - Endpoints used: `GET /2/users/me`, `POST /2/tweets` (create post), `POST /2/tweets` with `reply.in_reply_to_tweet_id` (reply), likes, `GET /2/users/:id/mentions`.
  - **Token refresh** against `https://api.twitter.com/2/oauth2/token` (grant_type=refresh_token). Must be transparent/automatic (401 → refresh → retry once → alert). No b64-guessing hacks.
- **X Account Activity API webhook (best for mentions):** registered webhook performs CRC (`sha256` HMAC of `crc_token` with consumer secret → `response_token: sha256=...`), then receives `tweet_create_events`. **This is the efficient, real-time mention feed.**
- **Browser automation (last resort / fallback):** logged-in persistent Chromium context for search, DM, and reply fallback. Only for what the API can't do.

### 3.2 Pitch MCP (`https://api.trypitch.co/mcp`)
JSON-RPC 2.0 over HTTP, `Authorization: Bearer pk_...`.
- Method `tools/call`, `name: create_demo_video`, arguments:
  ```
  url, instructions,
  voice: "Charon", subtitles: false, theme: "light", background: "ocean",
  shape: "rounded", inset: "0.75", browserHeader: "light"
  ```
  Response is SSE (`data: ` lines) → `result.content[0].text` → JSON with `jobId`.
- `get_job` with `{jobId}` → returns `status` (`COMPLETED/FAILED/ERROR`…), `artifacts.final_with_cards | artifacts.video | s3_url`.
- `get_credits` for balance.

### 3.3 Supabase (the datastore)
Project `jwswpryozfxzaocimadp.supabase.co`. REST with `apikey` + `Authorization: Bearer <key>`, upsert via `Prefer: resolution=merge-duplicates`.

Tables to retain (extend as needed):

**`mention_jobs`** (the video pipeline state):
```
tweet_id, user_handle, target_url, editor_job_id,
status (pending|rendering|delivered|failed|no_url_found|submitted),
s3_video_url, x_reply_id, created_at, updated_at
```
Dedupe key: `tweet_id` OR `(user_handle, target_url)`.

**`prospects`** (the CRM):
```
handle UNIQUE, name, url, segment, score, stage, last_touch,
next_action_date, touches, product_url, last_variant, outcome, notes, why
```

**`activities`** (action log): `ts, action, handle, segment, variant, detail, result`.

**`insights`** (single-row adaptive memory: `id=1`, `content`).

## 4. Job/pipeline state machine (canonical)

```
                 (mention detects URL)
pending ──► create_demo_video (Pitch MCP) ──► rendering
                                              │
                          polls get_job ──────┤
                            COMPLETED ────────► delivered   (reply posted w/ s3_video_url, x_reply_id)
                            FAILED/ERROR ─────► failed
                                            no URL in text ─► no_url_found (tracked, not processed)
```
- Every mention is tracked even with no URL (`no_url_found`), so nothing is silently dropped.
- Skip/dedupe: tweets from @trypitchdotco itself, `s3.trypitch.co` links (our own delivery), already-processed tweets.

## 5. Anti-ban & CAPTCHA handling (hard requirements, from the skill)

This is the most important part. The previous account `@adnanxpitch` was
**permanently banned in 6 days** by ignoring these rules (106 actions/day, 11+
sessions, DM bursts, copy-paste self-promo). The current account is
`@adnanspitch`, created 2026-08-09.

### 5.1 Hard caps (mirror `budget.sh`, keep synced)
| Action | Normal/day | Cold ramp/day (until 2026-08-30) |
|---|---|---|
| Likes | 50 | 12 |
| Replies | 15 | 3 |
| Follows | 15 | 3 |
| DMs (incl. follow-up) | 10 | 2 — **none at all before 2026-08-23** |
| Posts (original) | 4 | 1 |
| Quote tweets | 4 | 1 |
| Discoveries | 40 | 10 |
| Sessions/day | 3 | 3 (min 2h apart) |

- Rolling-hour burst cap: **max 10 ok actions / 60 min**.
- No 3+ consecutive identical actions; vary the pattern.
- Randomize delays (never fixed intervals; the DOM-pollers polling exactly every
  10s/30s/45s were a bot fingerprint).
- Keep to waking hours (08:00–23:00 local), bounded sessions, idle gaps are good.

### 5.2 CAPTCHA / challenge strategy for the rewrite
**Prevention > detection > solving.**

1. **API-first shift:** X API v2 and webhooks **never trigger CAPTCHAs**. Use the
   webhook for mentions, the API for posting/replies, and reserve the browser
   for search/DM/fallback. Fewer browser actions = fewer chances to trip.
2. **Single stealth browser instance:** one managed persistent Chromium context
   (patched automation flags — `navigator.webdriver`, UA, WebGL, plugins),
   shared across all browser work. Never multiple concurrent headless instances.
3. **Detection (must trip a circuit breaker, never auto-retry):**
   - Watch DOM/URL for: `iframe[src*="arkoselabs"]`, `/account/access` page,
     `[data-testid="challenge"]`, 403 responses, "unusual activity" prompts,
     rate-limit errors.
   - On detect: pause automation → snapshot DOM + screenshot → log `failed`/`skipped`
     to `state/activity-log.jsonl` → `circuit-breaker.sh --trip "<reason>"` →
     alert the operator (dashboard/webhook). Blind retry on a CAPTCHA = ban signal.
4. **Solve (two options):**
   - *Recommended:* **human-in-the-loop** — the managed browser is reachable via
     CDP / VNC / headed window; operator solves the Arkose FUNCAPTCHA once, the
     refreshed `storageState` cookies are saved, automation resumes.
   - *Optional:* automated solver (CapSolver/2Captcha) intercepting the Arkose
     blobs via network listeners and injecting the token.
5. **Circuit breaker:** 3 trips in 24h → `state/HARD_STOP` → everything refuses
   to run until a human runs `circuit-breaker.sh --reset`.

### 5.3 Self-healing
- If a selector/click fails: re-observe (screenshot + DOM), find the control by
  visible text/role, retry **once**, then log failed and move on. Never
  loop-retry (ban signal + burns budget).
- Never fake success. If you can't verify an action landed, it didn't — log
  `failed`, don't advance CRM stage.
- Verify logged-in identity at boot (must be @adnanspitch / @trypitchdotco for
  the right profile) before any action.

## 6. Why the old architecture was wrong (the rewrite's requirements)

Old design: 3–4 daemons, each own headless Chromium, fixed-interval DOM polling,
synchronous `urllib` inside `asyncio`, copy-pasted MCP/Supabase code, hardcoded
secrets and absolute `/home/adnan/...` paths.

| Old problem | New requirement |
|---|---|
| Multiple parallel Chromium instances (RAM + flag risk) | One managed browser, shared context, request-scoped pages |
| 10s/30s/45s tight DOM polling for mentions | Real-time X webhook + API; polling only where unavoidable, with jitter |
| `urllib.request` (sync) blocking `asyncio` event loops | Fully async `httpx.AsyncClient` everywhere |
| Duplicated MCP/Supabase/X code across 5 files | Single `core/` library: `config`, `x_client`, `pitch_mcp_client`, `supabase_client`, `browser` |
| Hardcoded tokens, keys, absolute paths | `.env` + secrets manager; paths relative to project root |
| Ad-hoc duplicate logic on both a webhook AND a DOM poller | One ingestion path (webhook primary, scanner fallback) into one job pipeline |
| Heartbeat-hack "status" (Supabase activities) | Real process supervision / health checks |
| `xurl` shell wrapper + b64 brute-force refresh | Proper OAuth2 token manager (refresh → retry → alert) |

## 7. Target architecture (the rewrite)

```
                    ┌────────────────────────────────────────────┐
                    │             X / Twitter sources            │
                    │  (API v2 + Account Activity webhook +     │
                    │   stealth browser only for search/DM)     │
                    └───────────────────┬────────────────────────┘
                                        │  events (mention, launch, intent)
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │           INGESTION (event-driven)         │
                    │  webhook handler · API pollers (jittered) │
                    │  unified browser scanner (single instance)│
                    └───────────────────┬────────────────────────┘
                                        │  normalized events
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │        CORE (async, modular library)       │
                    │  x_client (OAuth2 + auto refresh)          │
                    │  pitch_mcp_client (create/get/credits)     │
                    │  supabase_client (upserts + dedupe)        │
                    │  registry / pipeline state machine         │
                    └───────────────────┬────────────────────────┘
                                        │  jobs
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │        JOB QUEUE + WORKER (backpressure)   │
                    │  pending → rendering → delivered|failed    │
                    │  retries w/ backoff · idempotent           │
                    └───────────────────┬────────────────────────┘
                                        │  video ready
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │        DELIVERY (X API, browser fallback)  │
                    │  ack reply · final reply w/ s3_video_url   │
                    └───────────────────┬────────────────────────┘
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │   CRM + ACTIVITY LOG + LEARN LOOP          │
                    │  (writes the same state the skill reads:   │
                    │   activity-log.jsonl, prospects, insights, │
                    │   budget.sh / circuit-breaker.sh honored)  │
                    └────────────────────────────────────────────┘

                    ┌────────────────────────────────────────────┐
                    │  SAFETY SUBSYSTEM (cross-cutting)          │
                    │  caps · burst limits · pacing/jitter ·     │
                    │  CAPTCHA detector · circuit breaker ·      │
                    │  HITL alerting (CDP/VNC for solving)       │
                    └────────────────────────────────────────────┘
```

### Component responsibilities

1. **Ingestion** — a single, event-driven surface. Primary source: X Account
   Activity webhook (real-time, no CAPTCHA, no polling). Secondary: API
   `GET /2/users/:id/mentions`; keyword search via one stealth browser on a
   jittered schedule (never fixed tight periods).
2. **Core library** — thin shared modules, all async, all in `httpx`, no
   copy-paste:
   - `x_client`: tokens + refresh; 401 → refresh → retry once → alert.
   - `pitch_mcp_client`: `create_demo_video`, `get_job`, `get_credits` with
     retry/backoff and SSE parsing.
   - `supabase_client`: typed upserts/dedupe for `mention_jobs`, `prospects`,
     `activities`, `insights`.
   - `config`: env-driven, relative paths, secrets injection.
3. **Job pipeline** — a queue with state machine (`pending → rendering →
   delivered|failed|no_url_found`), idempotent handlers, retries with backoff,
   and per-job metadata (tweet_id, handle, url, job_id, s3_url, x_reply_id).
4. **Delivery** — ack reply immediately; deliver final reply with video link via
   X API; Playwright reply only as fallback.
5. **CRM + logging** — writes exactly what the skill reads
   (`activity-log.jsonl`, `prospects.jsonl`, `insights.md`) plus Supabase, and
   honors `budget.sh` + `circuit-breaker.sh` as hard enforcement.
6. **Safety subsystem** — enforced at transport level (rate limiter), action level
   (caps/burst), and browser level (CAPTCHA/challenge detector → circuit breaker →
   human alert; HITL solve path via CDP). Runs before every action, never after.

### Deployment shape (recommended)
Single long-running process (or a small supervised process group) with async
tasks, not N daemons:
- `ingest` task(s) — webhook consumer + jittered API/search pollers.
- `worker` task(s) — Pitch MCP render + delivery, concurrency-bounded.
- `scheduler` task — content/community/CRM session cadence (replaces cron +
  Hermes crons + runner loop) that respects caps & circuit breaker.
- Health endpoint reporting per-task status + last heartbeat.

## 9. Non-negotiable invariants (encode them in the rewrite)

1. API and webhook first; browser only as fallback or for unsupported actions.
2. One browser instance, stealth-patched, persistent session, HITL-solvable CAPTCHA path.
3. Fully async I/O; zero blocking calls in the event loop.
4. Every external call has timeouts + retry-with-backoff + circuit breaker on repeated failure.
5. All secrets from env; nothing hardcoded; paths relative to repo root.
6. All writes idempotent/deduplicated (tweet_id and (handle,url) dedupe keys).
7. Every action and its outcome lands in `activity-log.jsonl` (the skill's budget/learning input); do-not-contact and opt-outs are instant and permanent.
8. Human-like pacing is structural (rate limiter + jitter + caps), not a comment.
9. On any CAPTCHA/warning/limit → stop, trip breaker, alert human. Never push through.
10. The rewrite honors the existing skill files' stage model, variant tagging, and hard caps so the "brain" keeps working unchanged.
